# Session Memory: Collector scope correction and decision to move on

## Summary

The user corrected the collector direction: the intended input was only a small
amount of relevant information, not broad system inventory or an agent acting as
an orchestrator to keep finding what is installed. They requested reflection,

## Decisions & Rationale

- A byte/time/entry-bounded inventory is not necessarily a small, useful answer.
  The collector's default combines multiple categories; software-only and exact
  workspace flags still retain environment discovery.
- We optimized coverage and repeatedly treated unknowns as reasons for more
  readers, scans and review, rather than asking what facts were actually needed.
- Inventory cannot establish desired installation intent, relevance or runtime
  health. Heuristic groups and partial package proposals do not solve that gap.
- The orchestration criticism concerns the agent's iterative process. The code
  itself does not automatically execute follow-up scope requests or scan an
  unrestricted whole filesystem. Preserve that distinction in future summaries.
- The previous recommendation to wire partial YAML into the collector is no
  longer the next step. It would improve input consistency, not cure overscope.
- No fresh report-03 request or collector expansion remains active under this
  continuation. Earlier approval and offline verification remain historical;
  this is a user-directed course correction, not retroactive denial of approval.
- If reconsidered, start with one concrete question, the few required facts,
  exact read scope, small output and a stopping condition. This is a lesson,
  not an approved replacement design or a newly assigned implementation task.
