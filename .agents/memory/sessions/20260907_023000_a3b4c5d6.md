# Session Memory: Standalone Single-Cloud Network Topologies, G4 GPU Count Resolution & Custom Profiles

## Summary
Resolved the G4 GPU count mapping bug in `deploy-gcp` where explicit `--isaac-workstation-gpu-count 1` was bypassed, created custom profile documentation and a developer example, evaluated reference architectures, designed comprehensive standalone single-cloud network architectures for AWS, GCP, and Azure with clean Mermaid flowcharts and zero multi-cloud egress overhead, verified infrastructure capabilities, created `configs/profiles/studio-enterprise.yaml`, implemented GCP Flex-start (Dynamic Workload Scheduler) integration, and validated via dry-runs.

## Key Changes & Bug Fixes

1. **GCP G4 GPU Count & CLI Parameter Precedence (`deploy-gcp` & `src/python/config.py`)**:
   - **Root Cause**: `deploy-gcp` used `str(user_gpu_count) != "1"` to check if the user provided an explicit GPU count, but Click assigned a default of `"1"`. Consequently, explicit `--isaac-workstation-gpu-count 1` was ignored and fell through to machine family heuristics. The substring heuristic `elif "48" in instance_type` mapped `g4-standard-48` to 4 GPUs (intended for `g2-standard-48`), despite G4 having 1 GPU per 48 vCPUs.
   - **Resolution**:
     - Updated `--isaac-workstation-gpu-count` Click option choices to `["auto", "1", "2", "4", "8"]` with default `"auto"`.
     - In `GCPDeployer.main()`, used `click.get_current_context().get_parameter_source()` to reliably distinguish user-provided command-line arguments from default values.
     - Added dedicated G4 family mapping (`g4-standard-48` -> 1, `96` -> 2, `192` -> 4, `384` -> 8) separated from G2 (`48` -> 4) and A2 (`4g` -> 4).
     - Fixed help text typo (`60000 GPUs` -> `6000 GPUs`).
     - Added `Test_GcpGpuCountResolution` with 13 exhaustive unit tests covering all G4, G2, A2, and N1 permutations in `src/tests/deploy_command.test.py`.

2. **Custom Profiles Guide & Example Profile (`configs/profiles/`)**:
   - Created `configs/profiles/custom-developer.yaml` showcasing `tier: custom`, remote GCS state locking, auto `/32` IP restriction, Secret Manager integration, and zero Cloud NAT idle fees.
   - Authored `configs/profiles/README.md`: A beginner-friendly guide detailing the `v1alpha1` specification schema, security & cost trade-offs ($0 vs <$0.10 vs $35-$180/mo), resolution hierarchy, CLI flag precedence, and `isaac9s` TUI profile switching.

3. **Standalone Single-Cloud Topologies for Omniverse & Isaac (`.agents/references/plans/network-plans.md`)**:
   - Analyzed 3 reference repositories (`gcp-isaacautomator-study`, `GCP-Nucleus-Server`, `nucleus-terraform`).
   - Designed 100% standalone, self-contained architectures for the 3 major supported clouds (**AWS**, **GCP**, and **Azure**) eliminating cross-cloud latency and egress fees.
   - Provided clean, renderer-safe Mermaid flowcharts (single-line quoted labels with `\n`, zero raw HTML tags).
   - Created parity matrix across AWS, GCP, and Azure for ingress (ALB vs Cloud ALB vs App Gateway), compute, shared USD storage (EFS vs Filestore vs NetApp Files), secrets, and zero-trust access (SSM vs IAP vs Bastion).
   - Evaluated 4-way comparative rating: Standalone GCP (9.5/10), AWS (9.4/10), Azure (9.3/10) vs Monolithic VM Antipattern (5.0/10).
   - Cataloged document in `.agents/references/INDEX.md`.

4. **Infrastructure Verification & Studio Enterprise Profile (`configs/profiles/studio-enterprise.yaml`)**:
   - Conducted an architectural audit distinguishing what Isaac Automator automates (workstation compute, GPU drivers, Isaac stack, dual DCV/NoMachine 3D streaming, Cloud NAT, IAP, KMS, Secrets, GCS backups) vs. external shared studio infrastructure (Omniverse Nucleus Enterprise cluster, Port 443 Ingress ALB, and managed Filestore/EFS/NetApp NFS shares).
   - Created `configs/profiles/studio-enterprise.yaml` specifying enterprise zero-trust security, zero public IP, dual DCV/NoMachine streaming, GCS remote state locking, and metadata for co-located Nucleus and shared NFS integration.
   - Updated `list_available_profiles` and `load_profile_spec` in `src/python/config.py` to preserve `"raw": data` and expose `enable_flex_start`.
   - Documented Section 4 in `configs/profiles/README.md` covering why to use the profile (zero egress, 3D viewport streaming, CMEK, team locking) and an infrastructure responsibility breakdown.

5. **GCP Flex-start (Dynamic Workload Scheduler) Support & Web Verification**:
   - Web verification confirmed Google Cloud DWS Flex-start (`provisioning_model = "FLEX_START"`, `max_run_duration: 604800s`, `instance_termination_action = "STOP"`) natively supports G4 (NVIDIA RTX 6000 Ada) and G2 (NVIDIA L4) machine families. Flex-start queues provisioning requests during regional GPU stockouts and guarantees non-preempted execution for up to 7 days.
   - Pinned `scheduling: "flex_start"` and `max_run_duration_days: 7` in `studio-enterprise.yaml`.
   - Enhanced `deploy-gcp` parameter resolution so `flex_start` is automatically respected from profiles when not explicitly overridden on the CLI, and expanded `--backup-bucket auto` for Flex-start instances.
