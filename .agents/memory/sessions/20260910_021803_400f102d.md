# Session Memory: Dedicated IsaacAutomator Neo4j devcontainer service

## Summary

User requested a custom IsaacAutomator Neo4j container, Compose devcontainer integration,
and an updated evidence-graph implementation plan. Added the dedicated development
service; it is not the existing Arena container or an evidence ingestion adapter.

## Decisions & Rationale

- `.devcontainer/docker-compose.yml` defines app, automator-neo4j and neo4j-gateway.
- Neo4j 5.26.30 Community uses a pinned official base and a narrow custom Dockerfile.
  Generated credentials stay in a private service-owned auth volume. A compiled
  bridge passes the initial password to the upstream API via stdin, never OS argv.
- Non-root DB, dropped capabilities, internal-only network, separate data/log/auth
  volumes, authenticated readiness, resource limits, no plugins or file CSV imports.
- Docker 29 did not actually publish ports for the internal-only endpoint. Added a
  pinned non-root read-only HAProxy gateway, with no mounts/credentials, exposing
  only localhost 17474/17687. The DB retains no ordinary internet route.
- Devcontainer configuration preserves existing editor/agent settings, features,
  credential mounts and hooks. Active editor container was NOT rebuilt/replaced.
- Community cannot satisfy reader/writer RBAC. This is developer-admin infrastructure,
  not an agent-safe query backend. No MCP or credential forwarding to agents.

## Discovered Gotchas & Caveats

- The upstream image contains empty databases/transactions directories. Freshness
  checks must recognize that exact empty skeleton without treating initialized
  data or incomplete password seeding as safe to regenerate. Regressions cover both.
- HostConfig port bindings do not prove actual publishing: inspect NetworkSettings
  and probe the Docker host. Host loopback is not the running devcontainer's loopback.
- Named volumes persist across recreation but are not backups. Data and auth must
  be backed up/restored together. No rotation/restore/upgrade drill was performed.
